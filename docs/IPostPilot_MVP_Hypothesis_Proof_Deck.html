01 / Hypothesis

What the MVP is trying to prove

Hypothesis: Given a long-form video, historical creator examples, and human review, I-PostPilot can reduce the time needed to find acceptable short-form clips while preserving the creator's content and style signals.

Independent inputs

  • Creator preferences and editable persona.
  • Approved and rejected Shorts/Reels.
  • Long-form video with or without transcript.

Observable outputs

  • Ranked candidate windows.
  • Sentence-aware transcript.
  • Rendered 9:16 MP4 with captions.
  • Creator approval, rejection, and feedback.

Success evidence

  • Top candidates are acceptable.
  • Review time decreases.
  • Fewer timestamp corrections.
  • Creator-style choices are explainable.
02 / Build setup

The setup used to test the hypothesis

The MVP was intentionally built as a small, observable evaluation system rather than a fully autonomous production platform.

Runtime

  • FastAPI backend running on a GPU-enabled Ubuntu VM.
  • Browser-based workflow for creator setup and review.
  • SQLite for experiment records and filesystem artifacts for media.

Media and AI stack

  • FFmpeg/ffprobe for validation, normalization, and rendering.
  • Faster-Whisper for timestamped transcription.
  • OpenCV and deterministic scoring for lightweight visual and narrative signals.

Test design

  • Creator examples labeled approved or rejected.
  • Editable persona with an approval gate.
  • Ranked candidates followed by human approval, rejection, and annotation.
Why this setup: every important step is inspectable: inputs, profile signals, candidate rationale, timestamps, rendered output, and human feedback are all recorded so the hypothesis can be challenged rather than assumed.

08 / Honest limitations

What the current run exposed

Boundary quality

Older runs included fragments such as clips beginning with “so”, “because”, or a partial thought. Sentence-aware merging improves this, but word-level boundary evaluation is still required.

Persona depth

The persona is structured and editable, but most inferred values are deterministic aggregates rather than a trained creator-specific model.

Visual fidelity

Current visual matching uses lightweight brightness, contrast, aspect ratio, scene, and optional face signals—not learned visual embeddings or editing-rhythm models.

GPU performance

If CUDA is unavailable, CPU fallback preserves functionality but invalidates GPU throughput claims until the runtime is repaired.

09 / Proof protocol

How to prove the hypothesis with the current version

  1. Prepare archive: 5–10 approved and 3–5 rejected examples with matching transcripts.
  2. Build and approve persona: record profile version and selected rules.
  3. Run the same long-form video three ways: generic ranking, profile text ranking, profile text + visual ranking.
  4. Render the top 10: use the same 9:16 and caption settings.
  5. Human review: creator marks approve, reject, or edit and records time-to-first-acceptable clip.
  6. Compare: top-1/top-3 acceptance, correction count, review time, and rejection reasons.
MetricEvidence threshold to discuss
Top-3 acceptancePersonalized ranking should beat generic ranking on the same source.
Review timeCreator reaches the first acceptable clip faster than manual scanning.
Boundary correctionsFewer start/end edits after sentence-aware segmentation.
Style feedbackCreator can explain why the clip feels aligned or misaligned.

11 / Conclusion

The MVP has crossed from concept to testable product.

Proven now

  • End-to-end media-to-clip workflow.
  • Resilient media normalization.
  • Creator profile approval gate.
  • Sentence-aware candidates.
  • Rendered, captioned social clip output.

Next proof, not more features

  • Run controlled generic vs personalized comparison.
  • Collect creator approvals and rejection reasons.
  • Measure review time and corrections.
  • Repair CUDA before claiming GPU performance.
Bottom line: the current version can demonstrate the core hypothesis as a measurable workflow. The remaining question is no longer “can it produce clips?” but “does the creator prefer its clips, and does it save meaningful review time?”
12 / Fellow-user feedback

What reviewers should help us validate next

The final proof point is not whether the pipeline runs. It is whether creators and fellow users find the results useful, understandable, and close enough to their publishing style.

What worked

Did ranked candidates reduce the effort of scanning a long-form video? Were the rendered clips and captions easier to review than transcript-only suggestions?

What needs improvement

Did any clip start with an incomplete thought, miss important context, or feel mismatched with the creator's tone, pacing, framing, or caption style?

What to record

For each reviewer, capture the clip tested, approve/reject decision, rejection reason, timestamp corrections, and time to find the first acceptable clip.
